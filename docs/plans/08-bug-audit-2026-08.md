# Bug audit — August 2026

Findings from a five-domain audit run on `hotfix/repo-refresh-and-macos-arm64` (base `ba9a98a`).
Nothing here is fixed unless the entry says so. Every entry states how it was verified — read-only
analysis is labelled as such, so the shaky ones stay visibly shaky.

Ordering is by damage, not by area.

---

## P0 — data loss

### 1. `git_pull` destroys uncommitted work

`app/src-tauri/src/commands/git_ops.rs:969` (`pull_blocking`), fast-forward write at `:1024-1034`.

The doc comment at `:558` claims _"Refuses to pull when the working tree is dirty"_. No such check
exists. `pull_blocking` fetches, runs `merge_analysis` — which compares commits and never looks at
the working tree — and on fast-forward does `set_target` + `checkout_head(CheckoutBuilder::new().force())`.
`.force()` overwrites every colliding file.

Exposure is the problem: `git_pull_all` (`:347`) loops this over **every registered repo** and is wired
to the Dashboard "Pull all" quick action (`app/src/pages/app/Dashboard/parts/QuickActionsCard/index.tsx:57`)
with no confirmation dialog. Per-repo failures are swallowed at `:375`, so the user sees only a success
count. Single-repo pull is reachable from Changes, RepoDetail, the Branches row and DetailPane.

**Verified** by porting `pull_blocking`'s FF half verbatim and running it against a real repo:

```
before: file.txt = "MY UNCOMMITTED WORK"
result: Ok("fast-forward")
after:  file.txt = "v2-from-upstream"          <- work gone

real `git merge --ff-only`, identical state:
  exit 1 — "Your local changes would be overwritten by merge"
  file.txt untouched
```

**Fix:** run `repo.statuses()` with `include_untracked(true)` before the FF and bail with
`bad_request`, or switch to `CheckoutBuilder::new().safe()` and surface libgit2's conflict error.
Either way, `git_pull_all` needs a confirmation step and must report per-repo failures.

### 2. Fast-forward merge overwrites untracked files

`app/src-tauri/src/commands/git_ops.rs:679-684` (guard) and `:720`.

`merge_blocking` does guard against a dirty tree, but with `include_untracked(false)`. A tree that is
"clean except for untracked files" passes, then the force-checkout overwrites any untracked file the
source branch also carries — precisely the files `git_index.rs::is_protected` defends in `git_discard`
(`.env`, `*.pem`, `id_*`).

Second hole on the same guard: `.unwrap_or(false)` at `:684`. If `repo.statuses()` fails (index lock
held by a concurrent `git`, unreadable file) the tree is treated as **clean** and the force-checkout proceeds.

**Verified** the same way as #1: an untracked `notes.md` was overwritten where real `git merge` refuses.

**Fix:** `include_untracked(true)`, propagate the `statuses()` error instead of `unwrap_or(false)`,
and prefer `.safe()` over `.force()` on both FF paths.

### 3. `settings.json` is written non-atomically; a parse error silently factory-resets

`app/src-tauri/src/config/store.rs:77` (`fs::write`) and `:45` (`from_str(&raw).unwrap_or_default()`).

`save()` truncates and rewrites in place — no temp file, no rename. A process death mid-write leaves a
truncated file, and the next boot swallows the parse error and comes up at defaults: every repo record
(with `group_id`, `custom_logo_path`, `ssh_key_path`), every group, `pinned_repo_ids`, `scan_paths` and
`provider_settings` gone. The first subsequent `save()` makes it permanent. No backup, no error surfaced.

`#[serde(default)]` on `AppSettings` covers missing _fields_; it does nothing for malformed JSON.

**Read-only analysis** — the mechanism is two lines and unambiguous; a real crash mid-write was not staged.

**Fix:** write to `settings.json.tmp` + `fs::rename` (atomic on NTFS and POSIX), and on parse failure
rename to `settings.json.corrupt-<ts>` and surface it rather than defaulting.

## P1 — broken features

### 4. GitHub Enterprise cannot be connected at all

`app/src-tauri/src/providers/github.rs:1222-1224`, same logic in `commands/providers.rs:442`.

`verify_with_base` strips a `/api/v3` suffix and then appends `/user` — hitting the GHE **web** app,
not its API, which lives at `/api/v3/`. GitLab strips _and re-appends_ (`gitlab.rs:1025-1026`);
GitHub is the only provider where verify and runtime disagree about what the stored base URL means.
The frontend only persists the token after verify succeeds
(`app/src/store/actions/providers.actions.ts:104-140`), so no GHE host can be added — with either the
host root or the `/api/v3` form the onboarding placeholder suggests.

The test `github_verify_strips_api_v3_suffix_for_enterprise` (`github.rs:2094`) pins this exact
behaviour and is green, which is why it never surfaced.

**Verified** by reading both providers side by side against the GHE API layout.

**Fix:** use the configured base verbatim (`format!("{base}/user")`) to match `api_base()`, or append
`/api/v3` for non-`api.github.com` hosts in both `verify_with_base` and `ping_github_inner`. Rewrite
the pinned test with it.

### 5. Updater fallback offers the wrong CPU architecture

`app/src-tauri/src/update/github.rs:127-145`.

`pick_platform_asset` receives only `std::env::consts::OS`, never `ARCH`, and takes the first asset
with a matching extension. Computed against the live API response for `v0.10.2`:

```
windows -> Recrest_0.10.2_arm64_en-US.msi     <- x64 users get the arm64 MSI
macos   -> recrest-v0.10.2-mac-arm64.dmg      <- Intel Macs get the arm64 DMG
linux   -> recrest-v0.10.2-linux-x64.AppImage
```

This path runs whenever the plugin updater fails (missing/corrupt `latest.json`, signature mismatch,
network) — exactly when the user depends on the manual download.

**Fix:** pass `ARCH` and match the contract names (`recrest-v*-mac-arm64.dmg`, `-windows-x64.exe`, …),
falling back to the extension heuristic only when nothing matches.

### 6. Update banner: "Install" and "Download" do nothing

`app/src/components/organisms/banners/UpdaterBanner/index.tsx:43,47`.

Both buttons render with `size`/`variant`/`data-testid` and **no `onClick` and no `href`**. Only
Dismiss has a handler. `UpdaterBannerState.downloadUrl` (`store/types/ui.types.ts:15`) is never read.

Compounding it: the Rust side emits `updater://available` and `updater://progress`
(`src-tauri/src/update/mod.rs:36,51`) and the names are re-exported in
`app/src/lib/constants/events.constants.ts:22-23`, but **nothing in the frontend ever calls `listen()`
on them**. So the banner only appears at all via Settings → Developer → Updater Playground.

**Verified:** read the whole component; grep for the event constants outside the constants file
returns nothing. The existing `UpdaterBanner.test.tsx` only asserts the null state, so the suite is
green and blind to it.

**Fix:** wire install → `invoke(TauriCommand.CHECK_FOR_UPDATE, { autoInstall: true })`, download →
`openExternal(banner.downloadUrl)`, and add a `listen(UPDATER_AVAILABLE_EVENT)` → `setUpdaterBanner`
subscription.

### 7. `ahead`/`behind` is silently 0/0 unless the remote is literally `origin`

`app/src-tauri/src/git/status.rs:307-315` hardcodes `refs/remotes/origin/<branch>` instead of reading
the branch's configured upstream — which `git/branches.rs:63` does correctly.

**Verified:** with the remote renamed to `upstream` (a normal fork workflow), `ahead_behind()` returns
`None` and the DTO reports 0/0 while real git reports the true divergence. Every fork and every branch
tracking a differently-named remote branch shows "up to date" while arbitrarily far behind.
`pull_blocking:1000-1003` has the same hardcoding.

**Fix:** resolve via `repo.find_branch(...).upstream()`, falling back to the hardcoded name only when
no upstream is configured.

### 8. PAT scope labels break on i18next's namespace separator

`app/src/components/molecules/PatHelpPanel/index.tsx:82`.

i18next's default `nsSeparator` is `":"`, so any key containing a colon is split into a bogus
namespace. GitHub scopes include `read:user` / `read:org`, Bitbucket's are `account:read`,
`repository:read`, `pullrequest:read` (`shared/src/constants/providers.ts:55,78`). The `defaultValue`
swallows the failure, so the user sees the raw scope id.

**Verified** by running the app's own i18next 26.3.1 against the real `en/common.json`: 6 of 9 scope
labels fail to resolve. Bitbucket's "Required scopes" list is entirely unexplained ids. The
translations exist and are correct in both locales — they simply never render.

**Fix:** pass `nsSeparator: false` in the `t()` options at that call site (verified to resolve).

## P2 — wrong behaviour, contained

- **Stash list renders a literal template.** `locales/{en,de}/repos.json:205` has
  `"stash_index": "stash@{{{index}}}"`; i18next does not interpolate the triple brace, so every row in
  the Working Copy stash list shows `stash@{{{index}}}`. Verified by running i18next. Use `"stash@{{index}}"`.
- **MR detail shows "not found" while the list is still loading.**
  `app/src/pages/app/MrDetail/index.tsx:114` guards on `!pr`, derived from the PR **list**, which
  `MrDetail` never fetches. Deep-linking or hard-refreshing an MR route renders "not found" until the
  first poll lands, and permanently if the provider is disconnected. `detailLoading` is already
  selected at `:88` and simply not used in the guard.
- **Commits of removed repos are never purged.** `app/src/store/reducers/activityReducer.ts:37` handles
  none of `removeRepo.fulfilled` / `deleteRepo.fulfilled` / `forgetReposUnderPath.fulfilled`, unlike
  `branchesReducer` and `prsReducer`. Dashboard KPIs, the heatmap, the language mix and the Activity
  charts keep counting a deleted repo for the rest of the session. Verified with a vitest probe.
- **Listener leak in `useBranchesByRepo`** (`:50-56`) — the only one of five `listen()` sites without a
  `cancelled` guard. `reload` depends on `repoIdsKey`, which changes shortly after mount on the
  Branches page, so the first listener always leaks and then re-fetches branches for every repo on
  every `repo://status` event. Verified with a probe test (unlisten spy: 0 calls).
- **`git_clone` ignores the allowed credential types and every SSH-key setting**
  (`app/src-tauri/src/commands/clone.rs:96-105`). Cloning an SSH URL _with_ a PAT connected fails,
  because the callback returns `userpass_plaintext` regardless of what libgit2 asked for — and works
  if you disconnect the provider. `git_ops.rs::install_credentials:144` does this correctly; reuse it.
- **`saveSettings.fulfilled` has no ordering guard** (`app/src/store/actions/settings.actions.ts:109`).
  `IntensitySlider` dispatches on every step (`step={5}` over 0..100 → up to ~20 concurrent
  `update_settings` calls per drag); a late response rewrites the value backwards. Same shape for
  `pinnedRepoIds`. Verified at reducer level; real-world reordering frequency not measured.
- **One unopenable repo defeats the activity range cache permanently.** `list_commits` skips repos it
  cannot open (`commands/repos.rs:517`) without emitting a `totals` entry, so `planFetchWindow`'s
  `hasUnloadedRepo` stays true forever and every range switch re-walks the full window for all repos.
  Verified with a probe test.
- **Cyclic `[includeIf]` kills the process.** `commands/git_config.rs:193-231` recurses with no depth
  limit; for the global view `.unwrap_or(true)` treats every `includeIf` as matched, so libgit2's own
  guard never fires. A Rust stack overflow aborts — the whole app dies. Verified with a verbatim port.
  Unusual config, three-line fix.
- **Included keys are attributed to the parent config layer.** `commands/git_config.rs:371-388` —
  `Config::open` follows `[include]`, so the global layer shows a `user.email` it does not own plus a
  bogus editable `include.path` row; editing it writes a new entry that appears to do nothing.
  Verified with a real gitconfig pair.
- **Custom terminal command splits on whitespace** (`commands/terminal.rs:100-105`).
  `C:\Program Files\...\alacritty.exe` becomes program `C:\Program`. That is the default install
  location for most Windows terminals; the Test button reports the same confusing error.
- **401/403 never surfaces as "unauthorised".** All three providers wrap every non-2xx in
  `CommandError::internal`, so a revoked PAT shows `internal error: github 401 …` even though the
  `Unauthorized` variant and the localized copy both exist.
- **A revoked token still shows the account as connected.** `is_authenticated()` only means "a token
  string exists"; `username()` swallows every non-2xx into `Ok(None)`; Bitbucket doesn't call the API
  at all.
- **Open-PR lists are silently truncated at 50** on all three providers, with no indication.

## P3 — hardening, hygiene, latent

- **A test back door survives into release builds.** `providers/mod.rs:19-37` — `env_base_url_for` has
  no `#[cfg(debug_assertions)]` gate and every `api_base()` consults it **before** the user's own
  setting, so `RECREST_PROVIDER_BASE_URLS` redirects all provider traffic (PAT attached) to another
  host. Needs local control of the process environment, so not remotely exploitable — but it is a
  one-line fix and the current precedence is backwards.
- **Rust is not tested in CI at all.** `grep -rn "cargo" .github/workflows/` finds only
  `cargo install` in `e2e-tauri.yml`. `rust:check`, `rust:test`, `rust:clippy` and `verify` exist in
  `package.json` and are wired into no workflow. Consequence: Windows- and macOS-only `#[cfg]` code is
  first compiled in the release matrix, where `continue-on-error: true` turns a failure into a silent
  gap.
- **`release-tauri-beta.yml:174` uses `shopt -s globstar`**, which does not exist in macOS bash 3.2 —
  the same constraint this repo already documents in `release-tauri.yml:457`. The step aborts,
  `if-no-files-found: warn` + `continue-on-error: true` keep the job green, and the beta artefact
  simply has no macOS installers. The workflow has never run, so there is no log to confirm it.
- **`checksums` can publish a partial `SHA256SUMS.txt`.** `gh release download … || true` swallows a
  failed download; `sha256sum recrest-v*` then hashes whatever arrived and `--clobber` overwrites.
  The release notes instruct users to verify with this file. `verify-release` does not check it.
- **`RELEASE.md` is hand-maintained and never asserted against the tag** — and it becomes the `notes`
  field in `latest.json`, so a stale file advertises the wrong version inside the in-app updater too.
- **Unpinned mutable action refs in the signing path** — `dtolnay/rust-toolchain@stable` is a _branch_,
  running in jobs that hold `TAURI_SIGNING_PRIVATE_KEY` and `contents: write`.
- **`app/src/main.tsx:64` violates the literal-expression rule** that `CLAUDE.md` spells out, by
  hoisting `import.meta.env.MODE === "demo"` into a `const`. A real production build was run and
  `app/dist` still contains no `devStub` chunk — Rolldown folds it today — but the safeguard is
  weakened exactly where the docs warn against it, and nothing in CI checks it.
- **`useResponsiveSidebar:47-62` persists an automatic collapse as a user preference**, so one run at
  a narrow width permanently loses the real preference.
- **`v0.10.2` has four orphaned `.sig` assets** whose payloads were pruned — four `latest.json` URLs
  are live 404s. The hotfix prevents recurrence but does not repair that release.
- Smaller items: `git_config.rs:457` reports success on a discarded remove error;
  `git_ops.rs:903` silently leaves a new branch without upstream; `ide.rs:24` accepts `.ps1` wrappers
  that `CreateProcess` cannot launch; `clone.rs:155` strips non-ASCII folder names (`Übersicht` →
  `bersicht`); `status::read_status` is called outside `spawn_blocking` at ~15 sites;
  `activity.loading` is missing from both locale bundles; `ContributorRow:186` uses
  `toLocaleString()` without a locale; `prsReducer` keeps global `loading`/`error` under a per-repo
  fan-out; `uiReducer` does not prune `pinnedRepoIds`/`selectedRepoId` on repo removal.

## Fixed during the audit

**`release-tauri.yml` — the macOS verify step aborted before it ran.** Commit `f2b4ded`.
GitHub invokes `shell: bash` as `bash --noprofile --norc -eo pipefail`, so `-e` is already on and
`set -uo pipefail` does not clear it. Both mac legs build with `--target <triple>`, so the bare
`target/release/bundle/macos/*.app` glob never matched, `ls` exited 2, `pipefail` propagated it, and
the assignment killed the step before its first `echo`. Every macOS leg would have failed on the next
release, skipping `Publish contract-named installers` and leaving the download page with dead buttons.
Replaced with `find`, verified against bundle-present / bundle-absent / nested-`.app`. The same `-e`
trap made several `::error::` diagnostics unreachable elsewhere in the job; those captures now end in
`|| true` so the message is what the user sees.

## What the audit did not cover

No runtime verification: the app was never launched, so rendering, timing and platform-specific
behaviour are out of scope. No macOS hardware, so the arm64 signing fix from this branch remains
unverified end to end. E2E suites were not run.

## Clean areas — checked, nothing found

`auth/token.rs` (backend split, atomic write, `chmod 600`, sentinel migration); token leakage
(no secrets in logs, headers only, `ProviderSettings` holds only `base_url`); provider concurrency;
`git_index.rs::discard_paths_blocking` path traversal (libgit2 rejects both `../` and absolute forms —
probed directly); `is_valid_branch_name`; the branch-delete current-branch guard; `checkout_blocking`'s
use of `.safe()`; `git/scanner.rs` normalisation; `git/branches.rs` upstream resolution; `git/logo.rs`;
lock ordering across every `config`/`watcher` pair (no deadlock); `branchesReducer`, `shortcutsReducer`,
`useContentSearch`'s sequence guard; port/mode switching; the updater plugin path and its signature
verification; and the i18n bundles themselves — 1755 keys per locale, perfectly symmetric, zero
one-sided keys, zero interpolation mismatches, zero incomplete plural pairs.

Convention compliance is genuinely clean: zero `sx` props, zero files over 800 LOC, zero inline
`data-testid` literals, zero hardcoded visible strings, zero nested interactive elements, zero
icon-only buttons without an accessible name.
